The baseline

Make the contract boring.

Consistency beats cleverness. Model URLs around resources, use standard HTTP behavior, and make every collection query explicit and bounded. The examples below use an imaginary articles resource.

01

Naming & resource conventions

Prefer nouns, plural collections

Use lowercase, kebab-case path segments. Let the HTTP method express the action; avoid verbs in resource paths.

GET    /v1/articles
POST   /v1/articles
GET    /v1/articles/{articleId}
PATCH  /v1/articles/{articleId}
DELETE /v1/articles/{articleId}

GET    /v1/articles/{articleId}/comments

Keep URLs predictable

  • Use stable opaque IDs; never expose database implementation details.
  • Use query parameters for collection views, not path variants.
  • Use PATCH for partial updates and PUT for full replacement.
  • Version only for breaking changes, e.g. /v1.
  • Return JSON with Content-Type: application/json.
02

Filtering & sorting

Use documented, allow-listed fields and operators. Reject unsupported fields or malformed values with a clear 400; do not silently ignore them.

REQUEST
GET /v1/articles?status=published&authorId=u_42&createdAt[gte]=2026-01-01&sort=-createdAt,title&page[size]=25
Filter

Equality uses the field name. Define operator syntax such as [gte], [lt], and repeated parameters for multi-value filters.

Sort

Comma-separated fields; prefix with - for descending. Define a stable default order and append a unique ID as a tie-breaker.

Bound

Set a default page size and a hard maximum. Validate and document date formats, enums, and filter combinations.

RESPONSE
{
  "data": [
    { "id": "art_123", "title": "Designing reliable APIs", "status": "published" }
  ],
  "pagination": {
    "nextCursor": "eyJjcmVhdGVkQXQiOi...",
    "hasMore": true
  }
}
03

Pagination that scales

Use cursor pagination for changing data

Cursors perform reliably on large collections and avoid many offset-pagination surprises when records are added or removed. Make cursors opaque, stable, and bound to the query; clients should pass them back, not construct them.

GET /v1/articles?page[size]=25
GET /v1/articles?page[size]=25&page[after]=eyJjcmVhdGVkQXQiOi...

Offset is fine for small, static lists

For simpler use cases, page[number] and page[size] are familiar. Cap the size, define whether numbering starts at zero or one, and explain that concurrent changes can shift results.

GET /v1/articles?page[number]=2&page[size]=25

Always: use a deterministic order, return only the metadata clients need, and make the next-page mechanism explicit. Avoid expensive total counts unless clients truly need them.

04

Errors clients can act on

Use the standard RFC 9457 Problem Details shape (application/problem+json). Keep messages safe and stable; include a request ID for support and structured field errors for validation.

400 BAD REQUEST
{
  "type": "https://api.example.com/problems/invalid-query",
  "title": "Invalid query parameter",
  "status": 400,
  "detail": "The requested sort field is not supported.",
  "instance": "/v1/articles",
  "requestId": "req_01JABC...",
  "errors": [
    { "parameter": "sort", "code": "unsupported_field", "message": "Allowed: createdAt, title." }
  ]
}

Never return stack traces, SQL, tokens, or internal infrastructure details. Use stable machine-readable problem types and codes; clients should not have to parse human-readable text.

05

Choose status codes deliberately

200Successful read, update, or action with a response body.
201Resource created; include its representation and a Location header.
202Accepted for asynchronous processing; provide a way to check progress.
204Successful operation with no response body, commonly deletion.
400Malformed request, invalid query, or validation failure.
401Missing or invalid authentication credentials.
403Authenticated caller lacks permission.
404Resource does not exist (or is intentionally undisclosed).
409Conflict with current resource state, such as a duplicate.
412Precondition failed, e.g. an If-Match version check.
429Rate limit exceeded; include Retry-After when possible.
500Unexpected server failure; return a safe problem response.
503Temporarily unavailable; include Retry-After when known.

Use 201 for a successful create and 204 only when the response truly has no body. Keep status semantics consistent across the API.

Design for predictable clients. Document every supported parameter, bound resource use, and evolve contracts deliberately.
